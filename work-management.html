01 Scrum → SDD Mapping

Every Scrum concept has an SDD equivalent. The core shift: specs replace stories as the atomic unit of work, and AI agents replace manual coding.

The Biggest Shift

Specs are not user stories. A spec contains the full architectural design — API contracts, data models, system flows, and acceptance criteria. This precision is what enables AI agents to generate high-quality code on the first pass.

02 Azure DevOps Board Setup

How to configure Azure DevOps for spec-driven development. The work item hierarchy, board columns, and organizational structure.

Work Item Hierarchy

1

Epic

Owner: Product Owner / TPM

Business-level initiative or program milestone. Represents a strategic investment. Example: "Customer Portal v2.0" or "Billing System Modernization."

2

Feature

Owner: Product Owner + Architect

A deliverable capability within an epic. Decomposes into multiple specs. Example: "User Authentication Module" or "Invoice Generation Engine."

3

Spec (User Story type)

Owner: Architect

The atomic unit. An architecture-grade specification with API contracts, data models, and acceptance criteria. This is what agents implement. Example: "Implement OAuth2 Authorization Code Flow."

4

Task (optional)

Owner: Sr. Developer

Manual intervention items only — work that agents cannot do. Infrastructure changes, vendor coordination, manual testing, security reviews. Most specs need zero tasks.

ADO Work Item Type

Use the "User Story" work item type for Specs. This maintains compatibility with existing ADO reporting, dashboards, and queries. Rename the display label in your project settings if desired, but keep the underlying type as "User Story."

Board Columns (States)

1

Drafting

WIP Limit: None

Architect is writing the spec. Work items created here with initial scope and linked to parent Feature/Epic.

2

In Review

WIP Limit: 3 per Architect

Architect and Sr. Developer review for clarity, feasibility, and agent-translatability. This is the Spec Review Gate.

3

Ready

WIP Limit: ~2x team capacity

Spec passed review gate. Queued for implementation. TPM sequences based on priority and dependencies.

4

Implementing

WIP Limit: 2–3 per Sr. Developer

Sr. Developer translates spec to agent prompts. Claude Code agent team executes. Sr. Dev monitors, iterates, and integrates output.

5

Validating

WIP Limit: 3 per reviewer

Code review against spec. Acceptance criteria verified. Tests pass. Architect checks architectural compliance. PO validates business intent.

6

Done

Spec Verification Gate passed

PR merged. Deployed to target environment. Spec work item closed. Feature and Epic progress auto-updated in ADO.

Swimlanes & Organization

🏊 Swimlanes by Domain

Create horizontal swimlanes for each product domain (e.g., "Customer Portal," "Billing Engine," "Admin Tools"). Gives instant visual of where work is concentrated.

🏷️ Tags for Metadata

Tag every spec with: complexity (S/M/L), agent pattern (single/parallel/pipeline/lead-sub), domain, and priority tier. Enables powerful filtering and reporting.

📊 ADO Queries

Create saved queries: "Specs blocked in Review > 2 days," "Implementing WIP over limit," "Ready queue depth," and "Cycle velocity by size."

📈 ADO Dashboards

Build dashboards showing: cumulative flow diagram, cycle time distribution, specs by state, and velocity trend by complexity tier.

03 Ceremonies & Cadences

SDD ceremonies are lighter and more focused than traditional Scrum. Agent execution reduces coordination overhead — the focus shifts to spec quality and review throughput.

1

Cycle Planning

Replaces: Sprint Planning  ·  Every 2 weeks  ·  60–90 min

TPM facilitates. Architects, Sr. Developers, and Product Owner attend. Select specs for the cycle from the Ready queue, confirm sizing (S/M/L), identify cross-spec dependencies, and assign specs to Sr. Developers.

2

Daily Spec Sync

Replaces: Daily Standup  ·  Daily  ·  10–15 min (async option)

Sr. Developers and TPM. Quick status on each in-flight spec: on track, blocked, or needs iteration. Focus on blockers and agent issues. Much shorter than traditional standups since agents do the execution.

3

Spec Demo

Replaces: Sprint Review  ·  Every 2 weeks  ·  30–45 min

Product Owner, stakeholders, Architects, Sr. Developers, TPM. Demo completed specs against acceptance criteria. Show working functionality. PO accepts or requests changes.

4

Cycle Retro

Replaces: Sprint Retrospective  ·  Every 2 weeks  ·  30–45 min

All team members. Review process metrics: agent efficiency, first-pass acceptance rate, spec quality, prompt effectiveness. Identify workflow improvements. Dev Manager facilitates.

5

Spec Refinement

Replaces: Backlog Grooming  ·  Weekly  ·  45–60 min

Architects, Sr. Developers, Product Owner. Refine upcoming specs to ensure they pass the Review Gate. Validate that specs are clear, complete, and agent-translatable. Split large specs if needed.

6

Architecture Review

New ceremony  ·  Bi-weekly or monthly  ·  60 min

Architects, Sr. Developers, Dev Manager. Review architectural decisions, pattern compliance, technical debt, and cross-domain consistency. Ensure agent-generated code maintains architectural integrity over time.

Async-First Option

The Daily Spec Sync can be fully async via ADO board updates and a shared Teams/Slack channel post. If all specs are green and no blockers exist, skip the synchronous meeting. The ceremony is optional when the board tells the full story.

04 Estimation & Planning

Spec sizing replaces story point estimation. Size reflects agent work scope and complexity, not human effort hours.

Spec Sizing

Small (S)< 1 day
Single agent  ·  1–2 filesBug fix, single endpoint, UI tweak, config change, simple refactor
Medium (M)1–2 days
Multi-agent  ·  3–5 filesNew feature module, API + UI integration, data migration with validation
Large (L)2–5 days
Agent team  ·  6+ filesCross-cutting feature, new subsystem, major refactor, multi-service integration

Planning Metrics

📊 Velocity Tracking

Track specs delivered per cycle, broken down by size. Example: 8S + 4M + 1L = 13 specs/cycle. Trend over time to calibrate future planning.

Track: Specs per cycle by size

👨‍💻 Sr. Dev Capacity

One Sr. Dev can typically run 3–4 Small, 2–3 Medium, or 1 Large spec per cycle. Adjust based on domain complexity and agent maturity.

Baseline: 6–8 "S-equivalents" per cycle

⚡ Agent Multiplier

AI agents provide 3–5x throughput vs. traditional coding. But the bottleneck shifts to spec quality and review. Plan review capacity, not just implementation capacity.

Target: 3–5x output per developer

🛡️ Cycle Buffer

Reserve 15–20% of cycle capacity for unplanned work: production issues, urgent specs, agent rework. A cycle at 100% planned capacity will slip.

Target: 80–85% planned utilization

Don't Convert to Hours

Do not convert spec sizes to hours or story points. Spec complexity (S/M/L) reflects the scope of agent work, not human effort. A Large spec might take 2–5 days of agent execution but only a few hours of human orchestration and review. Traditional estimation models do not apply.

05 Spec Flow Through ADO

How a single spec moves through the Azure DevOps board from creation to completion, with ownership transitions at each gate.

1

Drafted

Owner: Architect

Architect creates spec work item in ADO. Links to parent Feature and Epic. Fills in spec template: scope, API contracts, data models, acceptance criteria. Adds complexity tag (S/M/L) and domain tag.

2

In Review

Owner: Architect + Sr. Developer

Architect moves spec to "In Review." Both Architect and Sr. Developer review for clarity, feasibility, and agent-translatability. Sr. Dev validates it can be effectively turned into agent prompts. Questions resolved before proceeding.

3

Ready

Owner: TPM

Spec passes the Review Gate. Queued for implementation in the next available cycle. TPM sequences based on roadmap priority, cross-team dependencies, and Sr. Dev capacity.

4

Implementing

Owner: Sr. Developer

Sr. Dev picks up the spec. Translates to Claude Code agent prompts. Selects agent pattern (single, parallel, pipeline, lead-sub). Agent team executes. Sr. Dev monitors, iterates on output, and integrates results.

5

Validating

Owner: Sr. Developer + Architect + PO

Code reviewed against spec. Each acceptance criterion mapped to delivered code. Full test suite passes. Architect checks architectural compliance. PO validates business intent is met.

6

Done

Verification Gate passed

PR merged and deployed. Spec work item closed in ADO. Feature and Epic progress auto-updated. Spec marked as delivered in TPM reporting.

Transition Comments

Every state transition in ADO should include a comment summarizing what happened. For "Implementing → Validating," the Sr. Dev should note which agent pattern was used, how many iterations it took, and any manual interventions required. This data feeds into cycle retros and process improvement.

06 Key Differences from Traditional Scrum

What fundamentally changes when AI agents handle the coding and specs replace stories.

❌ Traditional Scrum

Tasks are the unit of work. Developers spend most time writing code. Estimation is in story points reflecting human effort. "In Progress" means a developer is coding. WIP limits apply to tasks per person. Velocity is measured in story points burned.

✅ Spec-Driven Development

Specs are the unit of work. Sr. Developers orchestrate agents and review output. Estimation is spec complexity (S/M/L) reflecting agent scope. "In Progress" means an agent team is executing. WIP limits apply to specs per Sr. Dev. Velocity is measured in specs delivered.

❌ Traditional Bottleneck

Coding capacity. Need more developers to deliver more. Knowledge is distributed across many heads. Onboarding is slow. Estimation accuracy depends on individual developer experience with the codebase.

✅ SDD Bottleneck

Spec quality and review capacity. Need better specs and faster reviews to deliver more. Knowledge is captured in specs and CLAUDE.md. Onboarding is faster. Estimation accuracy depends on spec clarity and complexity calibration.

Don't Create Tasks Under Specs

The most common mistake when transitioning: decomposing specs into tasks the way you would with stories. Agents handle their own task decomposition. If you find yourself writing tasks under specs in ADO, either the spec is too large (split it) or you are micromanaging the agent workflow.

07 Bug Resolution & Reportability

How bugs are tracked, resolved, and measured in the SDD model. Bugs are first-class work items linked back to the originating spec, enabling root-cause analysis and continuous spec quality improvement.

Bug Handling in SDD

Bugs Are Spec Feedback

Every production bug is a signal about spec quality, agent output quality, or validation gaps. Link every bug to its originating spec in ADO. This creates a feedback loop: specs that produce more bugs get reviewed for systemic issues in their design, acceptance criteria, or test coverage.

Bug Work Item Flow

1

Reported

Owner: Reporter (any role)

Bug created in ADO using Bug work item type. Must include: reproduction steps, expected vs. actual behavior, severity (P0-P3), and link to originating spec. Screenshots or logs attached.

2

Triaged

Owner: Sr. Developer + Architect

Bug assessed for severity, root cause, and fix scope. Linked to originating spec. Classified as: spec gap, agent error, test gap, or environment issue. Sized (S/M/L) and prioritized.

3

Fixing

Owner: Sr. Developer

Sr. Dev creates a fix spec or patches directly depending on severity. P0/P1 bugs bypass the normal spec queue and are fixed immediately. Agent teams execute the fix. Root-cause documented.

4

Verifying

Owner: Sr. Developer + Reporter

Fix validated against original reproduction steps. Regression tests added. Reporter confirms the fix resolves the issue. Architect reviews if the bug exposed a spec gap.

5

Resolved

Fix deployed

Bug closed in ADO. Resolution time logged. Root-cause category recorded. If the bug originated from a spec gap, the originating spec is flagged for retrospective review.

Severity Levels

P0 — CriticalFix immediately
System down or data lossProduction outage, security breach, data corruption. Drop everything. Bypass spec queue.
P1 — HighFix this cycle
Major feature brokenCore workflow blocked for users, no workaround. Prioritize in current cycle.
P2 — MediumFix next cycle
Feature degradedWorkaround exists. Schedule as Small spec in next cycle planning.
P3 — LowBacklog
Cosmetic or minorUI polish, non-blocking edge cases. Groom into spec backlog when capacity allows.

Resolution Metrics

Mean Time to Resolution (MTTR)

Average time from bug reported to fix deployed, by severity level

Target: P0 < 4 hrs · P1 < 2 days · P2 < 1 cycle

Bug Resolution Rate

% of open bugs resolved per cycle. Tracks whether the team is staying ahead of incoming bugs.

Target: > 90% per cycle

Bugs per Spec Delivered

Production bugs traced back per spec. Identifies specs or domains that consistently produce defects.

Target: Track trend ↓

Root-Cause Distribution

% breakdown by category: spec gap, agent error, test gap, environment issue. Drives systemic improvement.

Target: Spec gaps < 20% of total

Reopen Rate

% of bugs reopened after being marked resolved. Indicates fix quality and verification thoroughness.

Target: < 10%

Escaped Defect Trend

Production defects per cycle over time. The primary quality trend line for executive reporting.

Target: Track trend ↓

Reportability Metrics

Bug reportability measures how well bugs are documented when filed. High-quality bug reports reduce triage time and enable faster, more accurate fixes.

Reportability Score

% of bugs filed with all required fields: repro steps, expected/actual behavior, severity, and spec link

Target: > 85%

Reproduction Rate

% of reported bugs that can be reliably reproduced from the filed report without additional context

Target: > 90%

Spec Attribution Rate

% of bugs linked to their originating spec. Enables spec-level quality tracking and root-cause analysis.

Target: > 95%

Triage Time

Average time from bug reported to triaged (severity confirmed, root cause classified, owner assigned)

Target: < 4 hours for P0/P1 · < 1 day for P2/P3

ADO Configuration for Bugs

Required Bug Fields

Configure ADO Bug work item with required fields: Severity (P0-P3), Repro Steps, Expected Behavior, Actual Behavior, Originating Spec (linked work item), and Root-Cause Category.

Bug Dashboard Widgets

Add to ADO dashboard: open bugs by severity, MTTR trend chart, root-cause distribution pie chart, bugs-per-spec scatter plot, and reportability score trend.

Bug Queries

Create saved queries: "Open P0/P1 bugs," "Bugs without spec link," "Bugs reopened this cycle," "Bugs by root-cause category," and "Stale bugs (open > 2 cycles)."

Cycle Retro Integration

Review bug metrics every Cycle Retro. Focus on: root-cause trends, specs producing the most bugs, reportability gaps, and MTTR outliers. Feed insights into spec quality improvements.
